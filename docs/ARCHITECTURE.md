# ApartmentOS — Architecture & Decisions

## Overview
Property management platform for Marcus Properties (marcus-properties.com), managing ~20 short-term rental and private properties in Jerusalem.

## Tech Stack Decisions

| Choice | Why |
|--------|-----|
| **Next.js 14 (App Router)** | Best Supabase SSR integration, Vercel-native, server components for fast loads |
| **PWA (not native Android)** | Faster to ship, single codebase. Manifest + service worker via `@ducanh2912/next-pwa`. Capacitor wrapper for native Android later (`output: 'export'` for that build) |
| **Supabase** | Postgres + Auth + Storage + Edge Functions + RLS in one platform. Client-managed via dashboard |
| **Tailwind + shadcn/ui** | Mobile-first utility CSS with accessible, unstyled components to customize |
| **Zustand + React Query** | Minimal client state (Zustand) + server data caching (React Query) via `Providers` wrapper |
| **iCal sync (not Lodgify API for calendar)** | Universal — works with Airbnb, Booking.com, Lodgify, any platform. Lodgify API used only for financial data. Sync interval: 30min (not 15min — avoids Airbnb rate limits) |
| **Claude Haiku / Gemini Flash for bill parsing** | ~80-100 docs/month at <$2/month. Cheap enough for the volume |
| **Resend for email** | Simple transactional email. Can add SMS/WhatsApp later |

## Architecture Patterns

### Authentication & Authorization
- **Admin:** Email/password via Supabase Auth
- **Owners:** Magic link email login via Supabase Auth
- **Contractors/Guests:** No auth — signed JWT tokens with expiry (magic links)
- **Middleware:** Authentication only (is user logged in?), NOT authorization (is user admin vs owner?). Authorization enforced at page/component level and via RLS
- **Route protection:** All admin routes (`/dashboard`, `/properties`, `/bills`, `/tasks`, `/financials`, `/calendar`, `/settings`) and `/owner` require auth. Public: `/contractor/[token]`, `/guest/[token]`, `/login`, `/api/webhooks`
- **RLS:** ALL tables have Row Level Security enabled. Owners only see their own data. Admin uses service role (`createServiceClient()` — server-side only, runtime guard prevents client usage)

### Data Model
- **Currency:** All amounts in agorot (integer). ₪1.00 = 100 agorot. Prevents floating point
- **Dates:** UTC in DB, displayed in `Asia/Jerusalem` timezone
- **IDs:** Supabase-generated UUIDs everywhere
- **API keys:** Stored in `app_settings` table, AES-256-GCM encrypted via `src/lib/encryption.ts`, managed via Admin Settings UI. Table has NO RLS policies = service role only access
- **Env validation:** All environment variables validated at startup via Zod schema (`src/lib/env.ts`)
- **Inventory:** Per-status quantity tracking (`quantity_in_closet`, `quantity_at_laundry`, `quantity_damaged`). Par level alerts compare `quantity_in_closet` against threshold
- **Owner stays:** Use `bookings` table with `platform = 'owner_stay'` convention
- **Cleaning tasks:** Distinguished via `is_cleaning` boolean on `tasks` table for turnover automation

### Security Model
- **RLS on every table** — no exceptions. Tables with no client-access policies (`app_settings`, `magic_links`, `revenue_tracking`) are accessible only via service role
- **Magic link tokens** validated server-side only — `magic_links` table has no SELECT policy for authenticated users
- **Commission rate** has CHECK constraint (0-1 range) preventing invalid values
- **Service client guard** — `createServiceClient()` throws if called from browser context
- **Encryption** — API keys encrypted with AES-256-GCM using `ENCRYPTION_KEY` env var (min 32 chars)

### Key Integrations
1. **iCal Sync** — Supabase Edge Function cron (every 30min) fetches iCal feeds, upserts bookings by UID. Exponential backoff on failures. Tracks `last_successful_sync` per feed
2. **Gmail Bill Parsing** — Gmail API webhook → Edge Function → AI extraction → `bills` table with `pending_review` status. **Note:** Personal Gmail OAuth has 7-day token expiry in Testing mode. Need manual "Reconnect Gmail" prompt in admin UI, or apply for OAuth verification early
3. **Lodgify API** — Called after checkout to fetch gross rental & channel fees for commission calculation
4. **Green Invoice** — Admin clicks "Push to Invoice" → API creates **draft** invoice (never auto-sends). Admin reviews before sending

### Magic Links
- Generated by admin, stored in `magic_links` table
- JWT signed with `jose` library, contains: property_id, task_id, link_type, expires_at
- Must validate `exp` (expiry), `iss` (issuer), and cross-check against `magic_links` table (supports revocation)
- Contractor links expire after task completion or manual expiry
- Guest links: entry code time-gated — hidden until 24h before check-in (page accessible earlier for instructions/video)

### Seasonal Maintenance
- Templates in `seasonal_templates` table with `month_trigger`
- Admin can CRUD templates via Settings (change dates, add new types, disable existing)
- Edge Function cron runs on 1st of each month, creates tasks from matching active templates for all active properties

### Bill Anomaly Detection
- On bill insert, query last 3 bills of same type for same property
- If new amount > 120% of average → set `is_anomaly = true`, status = `flagged`

## Infrastructure

### Error Handling
- `src/app/error.tsx` — global error page with retry
- `src/app/not-found.tsx` — 404 page
- React Query with `retry: 1` and `staleTime: 60s`

### Providers
- `src/components/providers.tsx` — `QueryClientProvider` wrapper, imported in root layout

### Database Migrations
- `00001_initial_schema.sql` — 16 tables, enums, RLS policies, indexes, triggers, seed data
- `00002_rls_fixes.sql` — enables RLS on 6 missing tables, adds policies for 4 tables, performance indexes
- `00003_schema_constraints.sql` — commission CHECK constraint, inventory model fix, `is_cleaning` flag
- `00004_messages.sql` — messages table for owner-admin messaging, property-scoped threads
- `00005_messages_admin_policies.sql` — admin RLS policies for messages (SELECT, INSERT, UPDATE)

### Design Direction
**Chosen: Ledger** (2026-04-03) — financial data as primary surface, entity-first navigation.
- Token file: `src/styles/tokens/ledger.css`
- DirectionProvider: `src/components/layout/direction-provider.tsx` (set to 'ledger')
- Brand: Marcus Properties copper `#E8734A` for CTAs, navy `#1E3A5F` as primary

### Modular Architecture
- **Design tokens:** `src/styles/tokens/base.css` (slots) + `ledger.css` (direction values)
- **Universal components:** CurrencyDisplay, DateDisplay, StatusBadge (work in any direction)
- **Feature modules:** `src/components/modules/` — self-contained with co-located React Query hooks
- **Direction shells:** `src/components/layout/shells/` — swap layout without touching modules

## Confirmed Decisions (from Client — 2026-04-03)
- **Lodgify is single source of truth** — full plan, all bookings (including phone) logged there
- **Green Invoice: draft mode only** — system creates drafts, admin reviews before sending
- **Gmail: personal account** — bills arrive as PDF attachments. Client plans to migrate to business email later. OAuth consent screen may need "Testing" mode initially
- **Contractor payments outside app** — app only records expenses/receipts and surfaces to owner. No payment workflow
- **Seasonal templates: editable** — default dates stay yearly, but admin can change dates, add new types, disable existing
- **Quarterly reports** — admin generates quarterly summaries for owners. Owners also have real-time raw data access in portal
- **Simplex combination locks** — no smart lock API. Entry codes manually entered/updated in admin. Codes rotated every few months. Chosen for Shabbat compatibility (no electronics)
- **Entry code time-gating** — guest check-in page sent ~1 week before arrival, but entry code hidden until 24h before check-in (property may still be occupied). Page shows instructions/video early, code reveals automatically based on booking check-in datetime
- **Laundry notifications via WhatsApp** — "Notify Laundry" uses `wa.me/` deep link initially, can upgrade to WhatsApp Business API later
- English-first UI, RTL-ready layout for future Hebrew support (CSS logical properties throughout)
- Canva designs treated as static image URLs (not live embeds)
- Single admin user initially (can scale to team later)

## Phased Rollout

### Phase 0 — Audit Fixes (DONE)
- RLS enabled on all tables, policies for all owner-accessible tables
- `app_settings` and `magic_links` locked to service role only
- Middleware protects all admin routes (not just `/dashboard`)
- Env validation with Zod, encryption utility for API keys
- React Query provider + error boundary wired in
- Service client uses base `createClient` with runtime browser guard
- Inventory model fixed to per-status quantities
- Commission rate CHECK constraint added

### Phase 1 — Foundation (Weeks 1-3)
1. `npm install` + install shadcn/ui components
2. Login page (admin email/password + owner magic link)
3. Admin sidebar navigation + mobile hamburger
4. Properties list + CRUD + tabbed detail (Overview, Bookings, Bills, Tasks, Inventory, Documents)
5. Owner management + tier assignment
6. Dashboard widgets (VAT tracker, property overview, pending items)
7. Document vault (upload, list, category filter, expiry tracking)
8. Settings page (API keys with encryption CRUD)

### Phase 2 — Operations (Weeks 4-6)
1. Magic link generation + contractor page (JWT, checklist, photo upload, expense capture)
2. Task board (list/board view, status filters, contractor assignment)
3. Seasonal template CRUD in Settings
4. Monthly cron Edge Function for seasonal task auto-creation
5. Inventory tracking (per-property linen counts, par alerts)
6. Laundry batch management (send/return, WhatsApp deep link)
7. Cleaning task automation (auto-create from booking checkout dates)

### Phase 3 — Financials (Weeks 7-9)
1. iCal sync Edge Function (30min cron, fetch/parse/upsert, backoff)
2. Fee calculator (commission from Lodgify, hourly from tasks, fixed monthly)
3. Bill parsing pipeline (Gmail OAuth, PDF extraction, AI parsing, verification queue)
4. Green Invoice integration (draft invoice creation from fee entries)
5. Quarterly report generation (PDF/email for owners)

### Phase 4 — Guest & Polish (Weeks 10-12)
1. Guest check-in page (Canva embed, YouTube, time-gated entry code)
2. Owner portal (tier-dependent views: Investor, Hybrid, Private)
3. Turnover calendar (visual booking calendar, gap hours, cleaning scheduling)
4. Notifications (Resend email for anomalies, assignments, low inventory)
5. PWA polish (`@ducanh2912/next-pwa`, icons, service worker, offline)
6. Testing (Vitest unit tests + Playwright E2E for login, magic link, bill approval)

## Known Risks & Mitigations

| Risk | Impact | Mitigation |
|------|--------|------------|
| Gmail OAuth 7-day token expiry (Testing mode) | Bill parsing breaks weekly | Build "Reconnect Gmail" prompt in admin UI. Apply for OAuth verification early (2-6 weeks). Or migrate to Workspace email |
| iCal rate limiting (Airbnb) | Booking sync blocked | 30min intervals (not 15). Exponential backoff. Track last_successful_sync |
| PWA manifest start_url `/dashboard` | Owners land on admin page | Detect user role and redirect. Or separate manifest per role |
| No Supabase project yet | Blocks all development | Provision immediately at Phase 1 start |
